# On-device relevance for bleib

[Q2 tests task-needs classifiers and local reasoning models, and traces the browser filter’s zero-correct result.](local-model-q2.md)

25 November 2026 · Run Q

## Decision

Use **paraphrase-multilingual-MiniLM-L12-v2 int8** as the reference model for an opt-in pilot with a preview. Keep automatic insertion off for the measured semantic rankers. MiniLM led on held-out F1 in both languages, yet close to half its picks were irrelevant and it missed both details in the Lisbon example. The accuracy gap is between finding text about a similar topic and deciding which fact would change the answer.

Run the pilot in the **wallet daemon** with ONNX Runtime CPU. The extension already reaches the wallet over authenticated native messaging, so both browsers can use the same bundled model and the same consent and receipt checks. Keep the browser WASM build as evidence that an extension-only runtime is feasible. With the daemon, both browsers and the desktop app share one installed model file. If bleib ships independent browser inference, bundle a second copy of the same pinned graph, tokenizer and policy configuration inside the extension. The measured archives fit both stores.

## Benchmark

The [fixture](../../spikes/local-model/data/drafts.tsv) contains 200 independently worded drafts across 100 paired scenarios, with 100 drafts per language. It covers trips, cooking, cover letters, coding, shopping, fitness, gifts, travel with kids, work email, health, money, location, ambiguous requests and attempts to extract unrelated details. It uses one synthetic, mixed-English-and-German [bleib with 40 entries](../../spikes/local-model/data/memories.tsv). The two versions of each scenario share labels and stay together in the split. Calibration used 48 drafts, 24 per language. The held-out set contains 152 drafts, 76 per language, with 26 empty-label drafts and 60 relevant entries per language. Ten held-out drafts test adversarial requests.

A label means a detail materially changes the requested answer. Each draft has zero, one or two labels. A protected detail can be relevant and still require approval. Generic questions, requests for somebody else, quoted instructions and attempts at bulk extraction should leave the selection empty. The Lisbon example follows the landing-page acceptance criterion and labels the aisle seat and vegetarian preference even though the draft leaves the mode of travel implicit. The labels were authored for this spike against a single synthetic person. The parallel drafts are correlated, and the labels have had one reviewer.

The keyword comparison calls the actual `relevance()` and `project()` from the source tree. `project()` adds term-overlap scoring, keeps one result per stored kind and caps the output at two. The extension also runs `draftProjection()`, which can reject a line that the chooser selected. The scoring comparison uses `project()` before that output filter. The two Lisbon facts share the stored kind `preferences`, which means the existing cap of one per kind makes the complete pair unreachable through that path.

Each model sees a draft and individual memory entries, with published query and passage prefixes for E5, published pooling, and cosine similarity. The spike ranks IDs, caps the list at two and permits two distinct IDs of the same kind. It uses one threshold per rank across both languages, in 0.01 increments, with a floor for the second pick at least as high as the first. It maximizes micro F0.5 on calibration, breaking ties by precision and then the higher combined floors. A floor of 1.01 disables that rank. Node determines the floors once and both browser runs reuse them. All reported precision, recall and F1 values are micro-averaged over entry picks on the held-out set.

In Node, MiniLM made 111 picks, of which 59 matched the labels. It picked something on 20 of 52 empty-label drafts and eight of ten adversarial drafts. It found 55 of 106 ask-only labels. Under a simulated existing automatic grant, the deterministic policy routed every ask-only pick to approval. Six of the ten remaining picks were still irrelevant. Confidence about relevance and permission to share address different risks.

The shipped keyword chooser picked something on 43 of 52 empty-label drafts. The current browser's factual-line filter reduced those to ten, and its final output found none of the labelled details in this corpus. In the Lisbon case both Node and WASM MiniLM picked the home location, which would require approval. None of the measured rankers selected either desired Lisbon detail. Node and WASM also differed on three MiniLM test drafts and seven E5 and IBM Granite drafts each. The community Granite int8 export produced near-identical Node scores across unrelated text and picked nothing in WASM at the Node floors. Pinning the model file alone does not guarantee identical selection across execution providers.

Use **0.37 for the first MiniLM pick and 0.53 for the second** when reproducing this experiment. Treat these as pilot thresholds. A release calibration should use fresh independently labelled memories and drafts, and select floors with precision as a release constraint. A reasonable starting gate is at least 90% precision per language for suggestions and 95% for automatic picks, with enough selected cases to estimate those rates and with recall and empty-draft behavior published alongside them. Across all five runnable exports, no threshold pair on the calibration grid reached even 90% precision with eight picks in each language. Keep bulk extraction, third-party drafts, explicit opt-outs and quoted instructions in the regression corpus.

## Gemini Nano

Chrome documents the Prompt API for extensions from **Chrome 138**, and for web pages from Chrome 148. From **Chrome 149**, supported text languages include English, German, Spanish, Japanese and French. The API needs a document and is unavailable in Web Workers. Eligibility includes Windows 10 or 11, macOS 13 or later, Linux, or a Chromebook Plus on ChromeOS platform 16389.0.0 or later. Chrome requires **22 GB free** on the profile volume and either **more than 4 GB of VRAM**, or **at least 16 GB of RAM and four CPU cores**. Chrome downloads the model initially on an unmetered connection, then runs it offline. The download size can change. Chrome may remove the model if free storage falls below 10 GB. [Prompt API and platform support](https://developer.chrome.com/docs/ai/prompt-api), [Chrome hardware, storage and language requirements](https://developer.chrome.com/docs/ai/get-started).

Playwright Chromium exposed `LanguageModel` in the extension document. With a fresh offline profile, `availability()` returned `unavailable` for both English and German. Firefox had no Prompt API global. Nano precision, latency, memory and download size therefore remain unmeasured. Its browser-managed provisioning and versioning preclude using it as the shared bundled default. An opt-in comparison on eligible Chrome hardware would need a provisioned model, the same labelled pairs, a schema-constrained list of IDs, and the same policy on every resulting ID. Browser-generated text would never enter the disclosure path.

1. **Choose eligible details inside the wallet.** After unlock, build vectors in memory and invalidate them on edit, delete, supersession, privacy changes, lock and model upgrade. Treat the vectors as sensitive derived data. Use raw text only with a pinned local tokenizer and encoder. Pass IDs and scores to the wallet's selector. The model has no access to tools, permissions or a write path.
2. **Train for task usefulness.** Prototype a task-intent layer or reranker with everyday contexts such as choosing a flight seat, finding suitable meals or using a known test runner. Include implicit tasks, hard negatives, personal exclusions, different vaults, code-switching and poisoned memory text. Evaluate on fresh people and scenarios. Allow two different slots across a capped two-detail result and retain the rendered length and factual-text limits. The Lisbon pair must pass in both languages before making that promise.
3. **Keep the phase-four boundary.** Use existing browser identity binding, owner approval, known composer and draft checks. Send the minimum draft needed for local selection over the allowlisted native messaging channel. Before releasing anything into the composer, revalidate exact entry IDs and versions, privacy, grant, destination and unchanged draft, then commit the receipt. A first share asks. Sensitive kinds, owner-private kinds and uncertain text always ask. Only consented everyday facts can use automatic sharing after the feature clears its accuracy gate. A mixed shortlist can omit protected facts without granting them permission. Keep previews literal and specific, with the actual task and details, accessible EN/DE controls, a clear Undo, and the existing protections against arbitrary provider text. [Phase-four verification](../../.planning/phases/04-browser-extension-save-and-fill/04-VERIFICATION.md), [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Firefox native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging).
4. **Abstain while loading or on failure.** Warm a single bounded worker after unlock and debounce draft changes. Drop stale requests. If the worker is cold, slow, missing or returns invalid scores, use empty automatic selection and leave the manual picker available whenever the wallet is unlocked. The older keyword matcher can assist a manual preview after the person requests one. Leave policy and receipt checks in the daemon even if a different renderer ever scores the candidates.
5. **Pin and verify each build.** Bundle the files in signed installers at build time, keep the model version fixed across browser and desktop, and run the same cases after every re-export.
