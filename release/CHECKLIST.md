# bleib 0.1 release checklist

Scope is the Chrome and Firefox extensions and desktop bleib on Linux and macOS. The extension and desktop installers currently use `0.1.0`. The separately versioned npm package is already published as `@bleib/wallet@0.2.0`. **Founder** marks account ownership, credentials, external submissions or final decisions. The remaining work can be delegated. Keep one record of the reviewed commit, tool versions, store IDs, artifact hashes, reviewers and release decisions.

## 1. Scope and accounts

- [ ] **Founder** · Decide which Linux distributions, package formats and architectures, macOS versions and architectures, and browser versions the first release will support. Current production manifests set Chrome 116+ and Firefox desktop 140+. The tested installer build is Linux amd64. List only the combinations that pass native acceptance. Windows, Safari, phones and hosted end-to-end encrypted sync are in development or deferred. Hosted sync is the later paid convenience.
- [ ] **Founder** · Register the Chrome Web Store developer account, pay the one-time fee, verify the email, enable 2-Step Verification and complete the account and distribution declarations shown in the dashboard, including trader status where applicable. Choose the publisher identity, a monitored support address and account recovery. [Chrome developer registration](https://developer.chrome.com/docs/webstore/register/), [distribution controls](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution).
- [ ] **Founder** · Create the Mozilla account for AMO Developer Hub, accept the distribution agreement and secure the account. Check any existing add-on records first. Claim the fixed Manifest V3 ID `bleib@bleib.dev` by uploading the first compliant package under that ID through the founder’s AMO account. Use that same add-on record for updates. Ask Mozilla about a conflict before changing the ID, which is also built into the native host. Pick the public URL slug separately. A listed submission may become public after signing, so use the release authorization in step 6 for the first listed submission. For an early signed candidate, use the unlisted channel and confirm the same GUID can be listed from the same record before proceeding. [Firefox IDs](https://extensionworkshop.com/documentation/develop/extensions-and-the-add-on-id/), [AMO signing channels](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/), [submission process](https://extensionworkshop.com/documentation/publish/submitting-an-add-on/).
- [ ] **Founder** · Enrol in the Apple Developer Program, accept current agreements and obtain a Developer ID Application certificate. Keep its private key and notarization credentials in a controlled keychain or secret store. Obtain a Developer ID Installer certificate if distributing a signed `.pkg`. [Apple signing](https://developer.apple.com/developer-id/), [certificate types](https://developer.apple.com/help/account/certificates/create-developer-id-certificates).
- [ ] **Founder** · Verify control of the npm `@bleib` scope and package, maintainers, 2FA and recovery. Agree on the next unused version and distribution tag. If using CI, configure an authorised trusted publisher and verify the chosen review and provenance settings. [npm package](https://www.npmjs.com/package/@bleib/wallet), [2FA for publishing](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/), [trusted publishing](https://docs.npmjs.com/trusted-publishers/).

## 2. Freeze the source and clear the policy checks

- [ ] Merge approved code into a clean candidate. Pin its commit, Node/npm versions and lockfiles. Keep package, installer, source archive and release notes traceable to that commit. Read the latest [extension instructions](https://github.com/rouxdutoit/bleib/tree/main/extension) and phase verification at the candidate.
- [ ] Resolve the [Firefox manifest](store/firefox.md#firefox-data-collection-and-transmission) and [Chrome in-product disclosure and consent](store/chrome.md#privacy-practices) blockers. Verify settings permit the controls described. Recheck data classifications and granted permissions against actual flows in both production builds. Use only `storage`, `nativeMessaging` and the three named host grants unless a change is reviewed and disclosed.
- [ ] Confirm EN and DE listing copy with the actual UI, including the inserted line. The reviewed commit uses a fixed English prefix. Confirm any later “About me” and “Über mich” labels on the final candidate. Add Chrome manifest localization for the short description. Publish matching English and German app privacy notices with local draft handling, native messaging, pairing, imports, provider disclosure on insertion, retention and deletion, user-sent reports, and Chrome Limited Use. Use the app privacy URL in Chrome and enter the privacy text in AMO. Verify both routes from a clean browser. [Chrome copy](store/chrome.md), [AMO copy](store/firefox.md), [screenshot plan](store/screenshots.md).
- [ ] Run lockfile installs, wallet lint and typecheck, extension typecheck, both unit suites, both dependency audits, and the two browser suites with Playwright Chromium and Firefox. Keep the fixture checks offline. Validate the workflow with `actionlint` and syntax-check both watcher scripts. Record the counts and failures at the candidate commit. Check license texts, bundled notices and source availability for distribution. Exclude test data, fixture builds, credentials, watcher code and desktop files from the extension archives.
- [ ] Build with `npm --prefix wallet ci`, `npm --prefix extension ci`, and `npm --prefix extension run build`. Zip the contents of `extension/dist/chrome` and `extension/dist/firefox` separately with `manifest.json` at each ZIP root. Inspect the actual ZIPs. Prepare the separate AMO source ZIP with the unbundled source, assets, lockfile and reproducible build instructions. [Chrome upload](https://developer.chrome.com/docs/webstore/publish), [AMO source package](https://extensionworkshop.com/documentation/publish/source-code-submission/).
- [ ] **Founder** · Upload the Chrome package as an unpublished draft and record the assigned Item ID without submitting for review. Confirm the ID on the package and later on the signed install. Use that exact 32-character ID as `BLEIB_CHROME_EXTENSION_ID` in both desktop production builds. An unpacked ID can be matched for testing via the dashboard public key. [Chrome manifest key and Item ID](https://developer.chrome.com/docs/extensions/reference/manifest/key).

## 3. Build and test the desktop installers

- [ ] On each supported OS and architecture, set `BLEIB_CHROME_EXTENSION_ID` and run `npm --prefix wallet run build:desktop`. The build copies the host Node binary, so verify that its architecture matches the package architecture. Each platform build recreates `extension/dist/desktop`. Copy and hash each final artifact before starting another build in the same workspace.
- [ ] Linux · Collect `extension/dist/desktop/bleib-wallet.deb`. Check package version, architecture, permissions and paths with `dpkg-deb`. Confirm `libc6`, `libgcc-s1`, `libstdc++6`, `zenity`, `libsecret-tools` and `xdg-utils` resolve. Test graphical installation, application-menu launch, login autostart and disabling it, upgrade of an existing memory, uninstall and reinstall. Confirm keyring write and read-back, lock and system unlock, owner-authenticated recovery export and recovery with an off-device copy. Test with a real unlocked desktop Secret Service, including a locked-keyring prompt. Treat distro browsers using sandbox portals as a separate acceptance case. The checked-in `.deb` builder does not produce RPMs or an APT repository.
- [ ] macOS · On real macOS, build `extension/dist/desktop/bleib.app` and verify the Swift Keychain helper, app launcher, bundle identifier `dev.bleib.wallet`, version keys and minimum OS. Verify the required app login behavior or document the manual launch step. Exercise new and existing installations, authentication, Keychain read-back, lock/unlock, owner-authenticated export and recovery from an off-device copy. Test on each offered architecture.
- [ ] macOS · Sign nested executables, including the Node runtime and the Keychain helper, then the enclosing app with Developer ID Application, a secure timestamp and hardened runtime. Check actual entitlements and verify signatures with `codesign`. If shipping a `.pkg`, sign the installer with Developer ID Installer. Keep the app signature valid through packaging. [Apple signing guide](https://developer.apple.com/developer-id/), [notarization troubleshooting](https://developer.apple.com/documentation/security/resolving-common-notarization-issues).
- [ ] **Founder** · Authorize Apple notarization using the project’s credentials. Use `xcrun notarytool submit <archive> --keychain-profile <profile> --wait`, review the notary log and require acceptance. Staple and validate the ticket on the appropriate app, DMG or PKG. If distributing a ZIP, staple the app and recreate the ZIP from the stapled app. Test Gatekeeper on a clean Mac with the artifact downloaded as a user would, including offline ticket validation. Record the notarization result and hash the exact deliverable. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution/).
- [ ] Verify native host registration for `dev.bleib.wallet` and the Chrome and Firefox IDs in a fresh standard user profile on every advertised OS/browser combination. Verify signed stock Firefox end to end, plus stock Chrome. Test a second profile and revocation, an existing wallet, denied connection, locked or stopped app, app and browser restart, and upgrade. An unpacked install and simulated Firefox framing are useful development checks. The signed-store pairing test is required for release.

## 4. Verify live providers and the page watcher

- [ ] **Founder** · Create and retain control of dedicated ChatGPT, Claude and Gemini test accounts with synthetic memories and no personal chats. Confirm usable test tiers and permitted automation. Keep reviewer access separate from watcher sessions.
- [ ] On stock Chrome and Firefox, confirm each live provider’s new-chat editor and memory variants. Test save before Send and Undo, review of sensitive and uncertain candidates, first share, later automatic ordinary fill, fresh sensitive approval, no match, per-site quiet-saving control, import into review, provider attribution, receipt and Undo. Test signed-out, missing or changed-page behavior. The site can see each addition as soon as it appears in the draft. Leave synthetic drafts unsent.
- [ ] **Founder** · Use separate headed Playwright login sessions to generate state for the three provider accounts. From `extension/`, run `npx playwright codegen --save-storage <private-temp-dir>/state.json <provider-url>` for each, then sign in normally with English UI. Start with clean drafts and at least one synthetic memory. Use a private temporary directory and delete each file after storing the raw JSON in its GitHub Actions repository secret.

| Provider URL | GitHub Actions secret |
| --- | --- |
| `https://chatgpt.com/` | `BLEIB_WATCH_CHATGPT_STATE` |
| `https://claude.ai/` | `BLEIB_WATCH_CLAUDE_STATE` |
| `https://gemini.google.com/` | `BLEIB_WATCH_GEMINI_STATE` |

- [ ] On the default branch, run `extension-watch.yml` manually and check the daily schedule at 05:29 UTC. Verify the no-secret path, all three successful provider runs, and that a controlled drift produces a deduplicated issue and seven-day redacted structural evidence. Check that the browser probe inserts and clears an unsent synthetic draft and checks the visible memory surface. Refresh expired sessions manually. A login challenge, CAPTCHA, rate limit or access block stops the affected check. Check that logs, artifacts and issues exclude secrets, raw provider text and real account screenshots. [Watcher workflow](https://github.com/rouxdutoit/bleib/blob/main/.github/workflows/extension-watch.yml).
- [ ] **Founder, optional** · If enabling Copilot cloud agent assignment, configure `BLEIB_WATCH_AGENT_TOKEN` with only the target repository permissions required by GitHub. Test controlled adapter drift in a suitable environment. The watcher assigns adapter drift only and issues may be created automatically. Require human review and the normal release process for any fix. Keep the token unset for human-only triage and for workflows where agent-authored patches conflict with funding commitments. [GitHub agent API](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api).

## 5. Independent security re-review gate

- [ ] **Founder** · Name an independent reviewer and supply the exact candidate source, threat model, manifests, permission and consent changes, installer build and test evidence. Include the replacement first-share and sensitive-consent rules and any changes after earlier internal review.
- [ ] Reviewer validates default and revoked access, per-provider binding, policy and receipt ordering, installer and keyring trust boundaries, browser-to-native framing and credential scope, update integrity, and the boundary between local matching and disclosure to a chat page. Verify recovery and existing-data behavior, and watcher data handling. Run relevant regressions and record the reviewed commit and disposition.
- [ ] Fix and retest release-blocking findings and send the changes for independent re-review. Confirm security fixes and review scope against the final signed artifacts. Public release stays closed until the independent re-review is complete and the founder records sign-off. A store review, a dependency audit and automated checks serve different purposes.

## 6. Store review and staged installs

- [ ] Finish the EN and DE listings and screenshots, category, single purpose, permission justifications, data declarations and support details. Give reviewers the exact desktop download and setup guide, the supported environment and a synthetic test path. Use Chrome’s Test instructions and AMO’s Notes for Reviewers. [Chrome test instructions](https://developer.chrome.com/docs/webstore/cws-dashboard-test-instructions). If credentials are needed, provide dedicated reviewer access through the platform’s private instructions.
- [ ] **Founder** · On the existing Chrome draft, set the extension as free, confirm the regions and submit for review with deferred publishing where available. If Chrome stages the approval, publish within the dashboard’s 30-day window or resubmit. To verify the signed build before public release, use the same item’s trusted-tester distribution and review flow. Confirm the store ID has not changed, then follow Chrome’s review flow for public visibility. [Chrome publishing](https://developer.chrome.com/docs/webstore/publish), [trusted testers](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution), [deferred publishing](https://developer.chrome.com/docs/webstore/update/).
- [ ] **Founder** · Submit the AMO source and package for signing. Use a signed unlisted candidate for the stock Firefox test if appropriate, then submit the listed version under the same ID when ready for a potentially immediate public listing. Confirm the public slug and the AMO-displayed ID. Check the state of automated validation and any further review. Resolve reviewer requests before calling the release complete. [AMO signing](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/), [submission and publication](https://extensionworkshop.com/documentation/publish/submitting-an-add-on/).
- [ ] Repeat native pairing and the first-share smoke test from both signed browser builds with the final desktop installers. Rebuild and re-review any change to code, permissions or package IDs. Refresh installer hashes and review notes as required.

## 7. npm and public release

- [ ] Inspect registry versions and tags with `npm view @bleib/wallet versions dist-tags --json`. Choose a fresh semver release from the reviewed commit. Keep the package and lockfile versions in sync. Leave the desktop and extension version independent. Run `npm --prefix wallet pack --dry-run`, inspect the actual tarball, and test install, `bleib --help` and a synthetic local setup from it under a clean prefix and the supported Node versions. Verify the license, CLI binary, dependency list and package contents.
- [ ] **Founder** · Publish only the reviewed npm tarball with public scoped-package access and the agreed tag after the security gate. For a staggered rollout, verify the candidate tag before moving `latest`. Verify package registry metadata, provenance if configured and a fresh install from npm. Retain the rollback tag and prior version. [npm publishing](https://docs.npmjs.com/cli/commands/npm-publish), [npm provenance](https://docs.npmjs.com/generating-provenance-statements/).
- [ ] **Founder** · Make the matching source, release notes, supported-platform instructions, signed desktop downloads and checksums available at the agreed release location. Publish the approved Chrome item and verify the AMO listing. Coordinate the companion download and store listing so each is usable when the other goes live.
- [ ] Verify public links and downloads in fresh profiles, including an end-to-end import, local save, first share and receipt. Watch store messages, compatibility jobs and support. Keep the previous artifacts and a store recovery path available. Escalate release-blocking reports to the founder.
